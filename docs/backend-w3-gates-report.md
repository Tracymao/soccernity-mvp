## 5. Judgment calls (adopted defaults, all veto-able)

1. **Uniform means uniform for restricted-pending; narrower for unverified.** A restricted-pending account has nothing to undo (it cannot have posted, followed or liked), so blocking unlike/unfollow/delete costs nothing and keeps one rule that cannot drift. For an *unverified* account, which may well have content from before this gate, blocking removal of its own content or leaving a club would be wrong, so only the creating forms are gated. (Both sets are in the table above.)
2. **Three routes the founder did not list stay open** because blocking them protects no one: notification and conversation read-state, and the kickoff-alert subscription (an earlier founder decision, `JwtAuthGuard`-only). Say if you want them blocked; each is a one-line change plus a row in the spec.
3. **The profile gate covers posting-class routes only**, not likes, saves, follows or club joins (those show the user only as the placeholder), and not Grassroots (a team page exposes no organiser identity) or Bants topics (the creator already passed the gate to make the room). #369 says "cannot post"; this is the narrowest reading that keeps it true.
4. **What an open incorrect-details flag does to the consent flow** (the OPEN point in #372): it **blocks approval and the card payment, not decline or withdraw** ("decline remains available"). Chosen over "flag only" because approving facts the approver has just said are wrong is not meaningful consent; chosen over a hard lock because the guardian can always decline and support can clear it. It **survives a guardian-email change** on purpose (the report is about the minor, not the guardian), so swapping in a different guardian cannot wipe it. Resolving it is support's call: a minimal admin list and resolve were added so the flag is operable, since a flag that blocks approval but cannot be seen or cleared would be a trap if the batches shipped out of order. The DOB-correction tool (B-103) will clear it as part of its restart.
5. **`username` set = profile complete.** Create Profile's other fields (Full Name, bio, picture, preferred club) are not required for the gate. If B-081 later requires more, only `isProfileComplete` changes.
6. **Approval email goes to `/login`**, not to a Create Profile route (which does not exist yet): the minor is usually logged out, and the login response's `nextStep` sends them on. It stays correct once Create Profile exists.
7. **`displayName` is no longer a fallback anywhere other users can see it**, including for legacy accounts. The `[deleted user]` sentinel written by the anonymisation sweep is the only displayName value still honoured (Decision Log #341). The owner still sees their own real name (`GET /users/:id`).
