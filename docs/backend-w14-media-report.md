## 1. What was built

| Area | What |
|---|---|
| Schema | `PostMedia` (migration `20261029100000_add_post_media`, purely additive, rollback in its header, CHECK constraints for the state machine). `Post.media` and `User.postMedia` are mechanical relations. |
| Upload link | `POST /media/uploads` (`JwtAuthGuard` + `GuardianConsentGuard`): validates the declared type/size against configuration, fails closed (503) for a video if the strip tools are missing, throttles per user, returns a one-time presigned `PUT` link into `quarantine/<uploaderId>/<uploadId>` bound to the content type and the exact length. |
| Confirm | `POST /media/uploads/:id/confirm`: claims the row, `HEAD`s the object, re-checks size, downloads to a temp file, checks magic bytes against the declared type, then strips metadata (images: sharp re-encode, EXIF removed, orientation applied; video: ffprobe + ffmpeg remux, no transcoding, first video/audio stream only, all metadata dropped), writes to `post-media/<uploaderId>/<uploadId>.<ext>`, deletes the quarantined original, queues the check. Video fails closed: 503, nothing stored, claim handed back. |
| Check | `MediaCheckService` + `PostMediaSweepService` (`@Cron` every minute): Rekognition `DetectModerationLabels` for images (downscaled for the check only above 5 MB) and for sampled video frames (interval and max frames in configuration), three outcomes from configuration thresholds (stricter for a minor), retry with doubling back-off, lease for crashed workers, give-up after N attempts, never approve by default, never overwrite a moderator. |
| Clients | `MediaModerationClient` (real `RekognitionMediaModerationClient`, in-memory fake in tests), `MediaProcessor` (real `FfmpegMediaProcessor`, fake video half in tests), `DirectUploadStorageService` (a subclass of `StorageService`, implemented by `S3StorageService`: `createUploadUrl`, `head`, `downloadToFile`, `uploadFile`). |
| Posts | `POST /posts`, `POST /banter-rooms/:id/posts` take `mediaIds`; `mediaUrls` is gone from both DTOs (a request carrying it is a 400). `POST /contest/final-entry` takes `mediaId` (exactly one video). All three go through `FeedService.createPost`. |
| Visibility | A post with any non-approved media is visible to its author only, on every read path (`post-media-visibility.util.ts`, ANDed into `visibleToViewer`, search, the anonymous view path, the contest entry list, pinned entry, carousel, impression endpoint, final ranking). A contest entry whose media is not approved is left out of the Phase 1 and final rankings. |
| Own-upload routes | `GET /media/uploads/:id` (status, reason, url), `DELETE /media/uploads/:id` (a contest entry's file is refused, 409). Another user's id is a 404 on every route. |
| Cleanup | Hourly quarantine purge (24 h, configuration); `DELETE /posts/:id` and account anonymisation delete the media rows and objects (anonymisation also strips the URLs from surviving posts). |
| Configuration | 22 new variables in `.env.example` and both services of `render.yaml`; `env-completeness.spec.ts` now also scans `this.num('NAME', ...)`; e2e key isolation pins the Rekognition keys to placeholders. |
| Old free-URL path | Not reachable from any user route. `MediaAsset`/`POST /admin/media/upload` (admin only) is untouched. |

## 2. What is stored, sent, retained and who can read it (for the DPIA drafter; not legal copy)

The full tables are in `services/api/src/modules/post-media/README.md`, section "What is stored, sent, retained and who can read it". Summary:

**Stored per upload (`PostMedia`, one row):** id, sequence, uploader id; kind; the declared content type and size; the processed file's content type, byte size and (video) duration; quarantine key (while the original exists); public key and URL; status (pending/approved/rejected), decision source (auto/moderator), decided at, decided by (a plain admin id); rejection reason; **check labels = moderation category names only** (no confidences, no image); check bookkeeping (state, attempts, next-due, lease, checked at, the last error's NAME); post id; created/confirmed times. Plus the processed file itself in the object store (and the unprocessed original until deleted, at most 24 h).

**Sent to Rekognition per call:** one still image as bytes (the photo, or one sampled frame of a video; at most 5 MB, larger images downscaled first) and a `MinConfidence` number. No user id, no account data, no filename, no URL, no text. Region `REKOGNITION_REGION`, default `eu-west-1`. Returned: label name, parent name, confidence; only the names at or above the pass threshold are stored.

**Retention:** original: seconds, at most 24 h; never-confirmed upload: at most 24 h; processed file and row: while the post exists, until the uploader deletes it, or the account is anonymised; check labels / decision fields: with the row. **No separate retention clock exists** for rejected files, labels or decision fields (OPEN, section 5).

**Who can read what:** the uploader reads their own row (never the check labels). Other users get a file's URL only through a post they can see, i.e. only once approved. The processed object is, however, in the public prefix before approval (OPEN, section 5). No admin endpoint exists yet. AWS (Rekognition) sees only the still image(s) for the duration of the call.

## 4. Known breakage and follow-ups caused by this change (not fixed here: backend only)

1. **`apps/web` is broken for the Final week upload until FC10.** `FinalWeekPanel` posts `mediaUrls` to `POST /contest/final-entry`, which now answers 400. The composer's own attachment controls were already disabled, so `POST /posts` from the web is unaffected (it sends no media).
2. **The Playwright harness in `e2e/`** (specs 15, 16, 17 and `e2e/support/contest-journey.ts`) creates final entries with `mediaUrls` and will fail for the same reason. Not run here.
3. `Message.mediaUrl` (direct messages) is still a free URL. Outside the brief; recorded so it is not mistaken for closed.
4. No admin endpoint approves/rejects (B-239/B-037), no notification is written on approve/reject (B-217), no "under review" flag on the author's own feed posts (the uploader reads `GET /media/uploads/:id`).

## 5. OPEN points I decided, with the default I chose (all veto-able)

| # | Point | Default chosen | Why / what changes if vetoed |
|---|---|---|---|
| 1 | Guards on the upload routes | `JwtAuthGuard` + `GuardianConsentGuard` only, as the brief says. NOT the verified-email and profile-complete guards that register row B-238 lists ("the same guards as POST /posts"). | Posting still needs all four, so an unverified or username-less user can upload but not publish. Adding `EmailVerifiedGuard`/`ProfileCompleteGuard` is two decorators and a `write-route-guards.spec.ts` row. |
| 2 | A processed file is in the PUBLIC prefix before it is approved | As the brief says (write to the public prefix). The API never returns its URL to anyone but the uploader, and the key contains two UUIDs, but anyone holding the URL can fetch it. | A rejected or unreviewed file (possibly unlawful) stays fetchable by URL. Safer: keep pending files in a private prefix and copy to the public prefix on approval (needs a `copy` on the storage abstraction). Recommended before launch. |
| 3 | Rejected files | Kept in the object store (not deleted on rejection) until the uploader removes them, the post is deleted, or the account is anonymised. | CSAM / evidence handling (B-206) is undecided, so deleting would destroy evidence and keeping may breach duty. Counsel call. |
| 4 | Thresholds | adult: pass 40, reject 90; minor: pass 20, reject 80. Reject categories: Explicit, Violence, Visually Disturbing, Hate Symbols. Sampling: one frame per 5 s, at most 30. | Pure configuration (`MEDIA_CHECK_*`). A reject category must be a top-level Rekognition moderation name; ancestors are walked, so a level-3 label reaches its level-1 parent. |
| 5 | Minor-stricter means lower thresholds only | Same reject categories, lower numbers. | A minor's file is held or rejected at lower confidence. A wider category list for minors would be a config change. |
| 6 | A minor's check is decided by the uploader's `isMinor` at check time | Fresh read of `User.isMinor`. | Not the age tier (under-16) and not the poster's contest status. |
| 7 | Formats | Images: JPEG, PNG, WebP (GIF and HEIC refused). Video: MP4, WebM, QuickTime/MOV. Animated WebP is flattened to its first frame. JPEG/WebP re-encoded at quality 90. | The brief says jpeg/png/webp. HEIC (iPhone default) is a real gap for the web composer (client converts, or server adds `heic`). |
| 8 | Video is remuxed, never transcoded | Codecs are not inspected, so a file with an exotic codec is accepted and may not play in every browser. Container kept (mp4/mov/webm); only the first video and first audio stream are kept. | As the brief says (no transcoding). |
| 9 | Limits | Image 10 MB, video 100 MB and 120 s, 10 files per post of which at most one video (images and a video may mix). | `POST_MEDIA_*`. The video limit is exact (120 s is allowed, 120.5 s is not). |
| 10 | Upload throttle | 30 links per user per hour, counted from `PostMedia` rows (so abandoned links count). `createdAt` is written from the app clock, not the database `now()`, so the window is testable. | `POST_MEDIA_UPLOAD_RATE_LIMIT_*`. A request for a link that is then refused (e.g. 400) writes no row and does not count. |
| 11 | Quarantine purge | Hourly job, rows with a quarantine key older than 24 h: never-confirmed uploads lose object and row; confirmed uploads lose only the original. No bucket-wide orphan scan. | Recommend a bucket lifecycle rule on `quarantine/` as a backstop (human step in `docs/deployment.md`). |
| 12 | Failed object deletes | Best effort after the database commit, logged with the key; no reconciliation job. | Applies to post deletion, anonymisation and the confirm step. A storage outage leaves orphaned objects. |
| 13 | Anonymisation | Deletes every `PostMedia` row and object of the user and removes those URLs from the posts that survive (#341 keeps the post). | This is the #419 item 9 vs #341 conflict the decision itself flagged: a surviving post loses its files. |
| 14 | Contest entries | An entry whose media is not approved when Phase 1 closes (or at the crown) is not ranked and cannot win; an owner cannot delete a contest entry's file (409). | The upload deadline (23:59:59 on day 24) leaves no time to review a held file before the reveal (00:00 on day 25): such an entry is simply not shown. |
| 15 | Removing a rejected file | `DELETE /media/uploads/:id` by the uploader; if attached to an ordinary post the post loses that file and (if nothing else is unapproved) becomes visible. There is no "edit post" to re-attach a corrected file. | "May be removed and resubmitted" is implemented as remove, upload again, and attach to a NEW post. |
| 16 | Check labels | Category names at or above the pass threshold, deduplicated and sorted; owner-hidden; not shown anywhere yet. | No admin read path exists. |
| 17 | Rekognition region and terms | `eu-west-1` (Decision Log #391). Whether AWS may use submitted images to improve its AI services (the Organizations AI-services opt-out policy) is NOT decided and not configured here. | Counsel/founder call before real keys are used. |
| 18 | Presigned link on R2 | `PutObject` with `ContentType` and `ContentLength` in the signed headers. Signing is unit-tested offline; **never run against a real R2 bucket**. The real size check is the server's `HEAD` on confirm. | Needs the bucket CORS rule and a real upload test. |
| 19 | ffmpeg on the host | `FFMPEG_PATH`/`FFPROBE_PATH`, default `ffmpeg`/`ffprobe` on `PATH`. Render's native Node runtime has neither, so on the current Render shape every video upload answers 503. | Needs a Docker image or another host with ffmpeg. The real ffmpeg code path IS exercised by `ffmpeg-media-processor.real.spec.ts` (8 tests: duration probe, audio-only/garbage refusal, mp4 / mov / webm remux with title, GPS-style location, comment and handler names proven absent from the output bytes, streams copied not re-encoded, JPEG frame extraction). It runs only where the tools exist and is skipped elsewhere (CI hosts without ffmpeg stay green); I ran it against an npm-packaged ffmpeg (a 2018 build, which also shows the flags need nothing new) and ffprobe 2023. The service-level video flow in the e2e suite uses the fake video half. |
| 20 | Confirm runs inside the request | A 100 MB video is downloaded, probed, remuxed and uploaded in one HTTP request. | Fine for a remux; a very slow store could hit a proxy timeout. A queued confirm is the alternative. |
| 21 | Confirm lease | A confirm stuck in `processing` is reclaimable after 10 minutes. | Constant in code. |
| 22 | Check lease | 10 minutes; back-off 1, 2, 4 ... minutes capped at 60; `MEDIA_CHECK_MAX_ATTEMPTS` 5; batch 10 per minute per instance. | Throughput of 10 checks per minute per instance; a busy launch needs a bigger batch or a faster cron. |
| 23 | Confirmed uploads that never reach a post | Kept indefinitely: only the QUARANTINE prefix has a 24 h clock. A verified, stripped, approved (or rejected) file that is never attached to a post sits in the public prefix until the uploader deletes it or the account is anonymised. | #419 sets no retention for it. A purge of unattached confirmed uploads older than N days is a small addition once N is decided. |
| 24 | The author cannot tell from the feed that a post is "under review" | Not built: `FeedPost` is unchanged. The uploader reads each file's `status` from `GET /media/uploads/:id`; the post simply does not appear for anyone else. | #419 item 5 says the uploader sees "under review"; the web (FC10) can show it from the upload status it already holds. A per-post flag on the feed payload is the alternative. |
| 25 | `Post.mediaUrls` is kept as a derived copy of the files' public URLs | The column still feeds the classifiers that decide photo vs video (`view-thresholds.util.ts`), the carousel and the admin contest views. URLs are copied at attach time; deleting a file removes its URL from the post. | Dropping the column in favour of the `PostMedia` relation would be a larger, separate change. |
